## 0.4.34 — 0.4.33 broke every connection (Xray's DNS module couldn't resolve the worker) · the real cause of the "mirrored" theme reveal in Persian (log koalix-20261108)
- **🩹 THE REGRESSION: 0.4.33's IPv4-first change.** Once `streamSettings.sockopt.domainStrategy` is set, Xray resolves its server's name through its **own `dns` module** instead of the system resolver. KOALIX's module was **DoH-only** (8.8.8.8 / 9.9.9.9 / 1.1.1.1), and those are unreachable on Iranian networks. Every proxy dial failed with `failed to resolve ip > features/dns: empty response`, so nothing loaded. (0.4.33's changelog wrongly said this was verified; `xray run -test` only checks syntax.)
- **🛡️ The fix: no lookup at all.** `XrayConfigBuilder.Build` now gets the IPv4 addresses KOALIX already resolved for the server at connect time (PoisonGuard: DoH-confirmed first, otherwise the system's). It pins them in `dns.hosts` and uses `domainStrategy = "UseIPv4"`. For anything else, the module tries the system resolver (`localhost`) first and keeps DoH only as a last resort.
  - Checked end-to-end with the real `xray.exe` 26.10.31 against the user's worker: **zero DNS queries**, `google.com/generate_204` → 204 and `youtube.com` → 200 in under 2 s, with no IPv6 dials.
- **🪞 Theme reveal no longer mirrors the app in Persian. This time it's the actual cause.** `RenderTargetBitmap.Render(Root)` draws an RTL element in its *logical* space, without the window's mirror, so the snapshot itself came out flipped (text backwards, sidebar on the wrong side). 0.4.33 only changed the `Image`'s FlowDirection, which can't undo that.
  - In RTL the snapshot is now flipped back with `TransformedBitmap(ScaleTransform(-1, 1))`.
  - It's verified with a screen-capture harness: the snapshot over the live UI is identical, and the reveal circle starts exactly under the clicked button.
- **🔢 Version:** 0.4.34. Every release now also ships a source zip in `release\`.

## 0.4.33 — Google/YouTube still hanging after 0.4.32: QUIC into a tunnel that can't carry UDP · Xray dialing the worker over IPv6 · mirrored theme reveal in Persian
- **🔬 Diagnosis: the worker is fine.** From the 0.4.32 session log plus direct probes: the same VLESS+WS worker, driven by a bare Xray SOCKS client (with and without sniff), returned `204` from `www.google.com/generate_204` and `200` from `www.youtube.com`, by domain and by IP. 0.4.32's fix worked (Chrome now reaches Google over IPv4 through the proxy). Two things were still left:
- **🚫 QUIC is now refused for tunneled traffic (new switch, on by default).** Chrome tries QUIC (UDP 443) first for Google and YouTube. A Cloudflare-worker tunnel (and any WS/gRPC/HTTPUpgrade transport) **cannot carry UDP**, so those packets vanished and Chrome waited before falling back to TCP, often long enough for pages and video to hang. `SplitPolicy.BlockQuic` makes `SplitRuleCompiler` emit an **early, pre-sniff reject** for `udp/443`, so Chrome gets an immediate "port unreachable" and uses TCP+TLS straight away. This is what v2rayN, Hiddify and NekoBox ship by default. The rule is scoped per mode:
  - Include mode: tunneled apps only.
  - Exclude mode: everyone except direct apps (exact paths and folder regexes, as inverted sub-rules).
  - Full tunnel: everyone except the engine.
  - xray.exe is never caught.
  - The switch is under Split tunneling ("Block QUIC (UDP 443) of tunneled apps", stored as `route.blockQuic`). Rule shapes were checked with `sing-box check` (1.14.4).
- **🌐 Xray dials its server IPv4-first.** The log showed `xray.exe` opening `[2a06:98c1:3122::]:443` (the worker's AAAA). Under TUN the gVisor stack accepts that instantly, but the real IPv6 path is dead, so each such tunnel connection hung ~14 s before being cancelled. Any domain-named server now gets `streamSettings.sockopt.domainStrategy = "UseIPv4v6"` (IPv4 first, IPv6 only if there's no A record), merged with the TLS-fragment sockopt when that's on. IP-literal servers are left untouched. Checked with `xray run -test` (26.10.31).
- **🪞 Theme change no longer "mirrors" the window in Persian.** The circular theme reveal shows a snapshot of the old look. In RTL the snapshot `Image` inherited `FlowDirection=RightToLeft` and was drawn flipped for the length of the animation. The snapshot is now `LeftToRight`, and the reveal hole's centre is mirrored into image space, so the wave still starts under the toggle.
- **✅ Tests:** 204, up from 198. Added: the QUIC reject per mode (include, exclude, full tunnel), its off switch, IPv4-first sockopt for domain servers, and its merge with fragment and absence for IP literals.

## 0.4.32 — the IPv6 reject that came one handshake too late: «ipnumberia خارجی می‌زنه ولی گوگل و یوتیوب باز نمی‌شن» (log koalix-20261107) · domain rules · foldable cards · skeletons · circular theme reveal
- **🩹 THE ROOT CAUSE — our own IPv6 guard, placed after `sniff`.** Google and YouTube publish AAAA records; ipnumberia.com does not. The tunnel (a VLESS worker) carries no IPv6, so KOALIX has long rejected global IPv6 for tunneled traffic. But that rule sat **after** the `{"action":"sniff"}` route rule. In sing-box's route matcher, a TCP connection that hits `sniff` leaves the *pre-match* phase, and gvisor then **completes the TCP handshake** before any later rule runs. So the browser's `[2a00:1450:…]:443` connection was *accepted* and then reset mid-stream. Chrome treats that as a broken connection, not as an unreachable address, so it never fell back to the working IPv4 address. Result: the IPv4-only test site loads with a foreign IP, while every dual-stack site (Google, YouTube, most CDNs) hangs or errors. The same config works in other clients because they don't add this rule, or add it before sniff.
- **🛡️ The fix — reject before sniff.** `SplitRuleCompiler` now emits **early TCP rejects ahead of the sniff rule** (`{"network":"tcp","ip_cidr":["2000::/3"],"action":"reject"}`). These are answered in pre-match: an RST to the SYN, so the browser falls back to IPv4 **instantly**. They're added for every mode where IPv6 can't ride the tunnel: the global leak block, full tunnel, include mode (tunneled apps only), and exclude mode (as a logical AND with inverted `process_path` / `process_path_regex` sub-rules, so direct apps and xray.exe keep native IPv6). Blocked apps' TCP is now refused before sniff too. The old post-sniff rejects stay as the UDP backstop. Nothing is emitted when the tunnel does carry IPv6. The health-inbound rule is inserted right after the sniff rule (`SplitRuleCompiler.AfterSniff`), whatever early rules precede it. Rule syntax was checked with `sing-box check` (1.14.4).
- **ℹ️ strict_route** is left at the user's choice (it was OFF in the field log). This fix doesn't depend on it.
- **🌐 Domain rules (Split tunnelling page → new "Domain rules" card):** one domain per line, for *always via tunnel* and *always direct*. Each covers the domain and all its subdomains. Pasted URLs are normalised: scheme, path, port and `*.` are stripped, then lowercased and de-duplicated. Rules compile **before** the per-app split (`domain_suffix`), and each comes with a matching DNS rule: tunnel domains resolve via remote DNS, direct domains via local DNS. Tunnel domains also get an IPv6 reject when the tunnel lacks IPv6. They apply on the next connect.
- **🗂️ Foldable dashboard cards** (`CardFold`): click a card title (quick actions, map, speed, apps, latency, usage, egress, conflicts) to fold it down to its header. It animates smoothly, a chevron rotates in the gutter, and the fold is remembered per card. Bindings inside the card are never touched; it's only clipped.
- **✨ Skeleton loading** (`Skeleton`): shimmering placeholders replace "…" while the ping is being measured, and skeleton rows appear while a subscription is importing. The shimmer pauses when the placeholder is off-screen and stays static with animations off.
- **🌗 Circular theme reveal:** switching light/dark now uncovers the *live* new theme in a growing circle from the sun/moon button. An accent-coloured ring rides the edge and the glyph spins and pops: sun in dark mode, moon in light mode. Changing the **accent colour** plays the same reveal from the swatch you clicked. Rapid changes (typing a hex) apply live instead of stacking snapshots. The reveal is skipped in safe mode and with animations off.
- **🧪 Tests:** 8 new ones. They cover pre-sniff placement for the include, global, exclude and blocked-app cases, no early rules when IPv6 is tunneled, the health rule landing right after sniff, domain parsing, and domain rules preceding the app split with matching DNS. Total: **198/198 pass**.

## 0.4.31 — the sinkhole kill-net: poisoned dials now die in one packet, not in a tunnel timeout (log 355 — the «بازم ipnumberia میاد بالا ولی گوگل نه» session)
- **🩹 THE FIELD LOG (19:53, uploaded as logs.txt) — the leak was still wide open.** `TUN: stack=gvisor, strict_route=False, mtu=1280, dns_doh=True` — **strict_route OFF**, i.e. the session ran a **pre-0.4.30 build** (the 0.4.30 startup migration `tun.strict.migrated` would have flipped it ON; that flag was never in this binary). And exactly the predicted flood followed: Chrome dialled **`[2001:4188:2:600:10:10:34:35]:443` — the ISP's poisoned AAAA with the 10.10.34.35 sinkhole embedded — 104 times** through a healthy TUN (`inbound/tun[tun-in]` → `outbound/socks[proxy]` → Xray → the ZEUS worker), each dial hanging until the tunnel timeout while the unblocked ip-check site loaded fine. Nothing was wrong with the VLESS/WS config, the subscription, or the tunnel — the browser was handed poison AAAA answers that bypassed the TUN, and the tunnel faithfully carried them to a dead address.
- **🛡️ The v0.4.31 fix — three layers, so the symptom dies even when a layer is off:**
  1. **Sinkhole kill-net (the new belt-and-braces layer):** the generated sing-box config's **FIRST route rule is now `{"action":"reject","ip_cidr":["10.10.34.0/24","2001:4188:2:600::/64"]}`** (`PoisonGuard.SinkholeCidrs`, applied via `SingBoxBuildOptions.RejectSinkholes`, tied to the existing PoisonGuard switch). It sits **before** the `ip_is_private → direct` rule — which would otherwise match the IPv4 pool and politely send the sinkhole DIRECT. A poisoned answer now costs the browser **one instant connection-refused**: Chrome falls back to the other address family or re-resolves through the tunneled DoH, instead of hanging 2–8 s per dial inside the tunnel. Works with every stack, needs no WFP, independent of strict_route.
  2. **strict_route ON stays enforced by the 0.4.30 one-time migration** (`tun.strict.migrated`) — anyone who still sees the flood simply hasn't run a 0.4.30+ build yet; the moment they do, the WFP rules pull the leaked lookups into the TUN and the poison disappears at the source.
  3. **Self-identifying logs:** every engine start now stamps **`KOALIX v{version}`** right under the `TUN: …` line (`SingBoxEngine.AppVersionTag`, set from `UpdateService.CurrentVersion` in AppHost), and the TUN line gained **`sinkhole_reject=`**. Log 355 cost analysis time precisely because nothing in it named its build — never again: a field log now testifies which binary produced it.

## 0.4.30 — the Windows DNS-leak hole: «وصل می‌شه، آی‌پی خارجی می‌زنه، ولی گوگل و یوتیوب باز نمی‌شن» (log 354 — strict_route shipped OFF for five versions)
- **🩹 THE BUG — the tunnel was healthy the whole time; the LOOKUPS were poisoned.** The field report: «یبار وصل می‌کنم، می‌رم تو سایت ipnumberia.com میاد بالا و ایپی خارجی زده، ولی گوگل و یوتیوب و هیچی بالا نمیاد؛ سایتا داخلی میاد انگار» — with «همه نوع تنظیمات» tried. Root cause: the **v0.4.15 decision to ship `strict_route` OFF** (out of WFP-clash caution). Without it sing-box installs **no WFP rules**, so Windows' "ordinary DNS requests" (svchost.exe → the Wi-Fi adapter's ISP resolvers, `2a03:ef42:…`) **bypass the TUN entirely** — the ISP answers blocked domains with the sinkhole (10.10.34.x / its IPv6-mapped 2001:4188:2:600:: form), the browser dials the dead destination through the tunnel, and every foreign site times out. That is the whole picture: **ipnumberia works and shows a foreign IP (unblocked name → clean answer → tunneled), Google/YouTube never load (blocked name → poisoned answer → dead destination), Iranian sites always load (unblocked + direct-friendly), and the occasional «بعد یهو درست شد» is the poison TTL expiring**.   1. **strict_route defaults ON** (engine mapping `settings.Get("tun.strict") != "0"` in AppHost, the Settings VM load, and ResetDefaults). sing-box now installs the WFP rules that force those lookups into the TUN, where `hijack-dns` answers them through the poison-proof remote DoH — exactly the path the 0.4.28/0.4.29 work built and then left unreachable behind the leak.
  2. **A one-time migration** (`tun.strict.migrated` in `AppHost.Build()`): every existing installation flips ON exactly once on first launch of 0.4.30 — an off-state from the v0.4.15 era was a workaround choice, not a considered verdict, and it is what kept this hole open. A user who switches strict routing back off afterwards is **never re-flipped** — their later choice is final.
  3. **The OS resolver cache is flushed** (`ipconfig /flushdns`, best-effort, bounded 3 s, failures logged) **the moment the tunnel is up and right after teardown** — so poisoned entries cannot outlive the topology they were learned in. Without this, a sinkhole entry (TTL up to 300 s) keeps sending the browser to a dead destination for minutes *after* everything else is fixed — the residual «یهو درست شد» lottery.
- **⚙️ Doc/comments synced:** the SingBoxEngine `StrictRoute` summary and the Settings page labels (fa/en) now say what the switch actually does («جلوگیری از نشت DNS — پیشنهاد: روشن» / «blocks the Windows DNS leak — recommended ON») instead of the old vague "extra leak protection".
- **🧪 `DnsLeakGuardTests` (7 tests):** the engine mapping is pinned to `!= "0"` (a regression to the old `== "1"` default-off form fails), the Settings VM load + ResetDefaults are pinned ON, the one-time migration must read AND write its latch (a migration that cannot run exactly once either never fires or overrides forever), the DNS flush must be a real bounded `ipconfig /flushdns` that runs **after** `engine.StartAsync` in ConnectAsync and inside TeardownAsync, and the generated AND merged sing-box configs must carry the `strict_route` flag into the TUN inbound.

## 0.4.28 — the DNS-poisoning shield (the audited «همهٔ کانفیگ‌ها وصل نمی‌شن» root cause), honest HTTPS probes, and the engine hardening set (fragment · mux · TUN MTU)
- **🛡️ THE FIX — DNS poisoning of the proxy server's own name, found by the external audit the user ran (Claude):** xray.exe / sing-box dial the proxy server **by name through the Windows system resolver** — and Iranian ISPs poison exactly those answers. The field log showed `demo7sample0.samplezeus.workers.dev` resolving to `188.114.98.0` / `188.114.99.0` — "last octet zero" addresses real DNS never returns — while DoH for the same domain answered the genuine `172.67.149.2` / `104.21.29.126`. That is the whole «بعد ۴۰ ثانیه یهو کار میکنه بعد دوباره وصل کنی هیچی نمیاره» lottery: a poisoned cached answer → the TCP dial connects but the TLS/WS handshake dies with EOF; the cache expires → it works; five minutes later it's poisoned again. **The fix — `PoisonGuard` (Koalix.Tunneling):** before every connect the server name is resolved TWICE, once through the system resolver and once over **IP-based DoH (8.8.8.8 / 9.9.9.9 / 1.1.1.1 — no bootstrap, untamperable)**; on disagreement the engine dials the **DoH-confirmed IP directly while the domain stays in SNI/Host** (TLS and websocket handshakes stay byte-identical; the SNI is forced back to the domain when the node had none, so certificates keep validating). Overlapping answers change **nothing** (a working connection is never touched), DoH-unreachable changes **nothing**, verdicts cache for 10 minutes, and every decision is logged in one honest line (`PoisonGuard: … dialing 104.21.29.126 with the domain kept as SNI/Host`). For panel/user JSON configs the companion upgrade points `route.default_domain_resolver` at a **DoH server with detour=direct** (outbound server names resolve through the encrypted channel instead of the hijackable UDP resolver) — only when the guard actually proved DoH is reachable, and never overriding a config that ships its own `default_domain_resolver`. The Xray config additionally carries an independent DoH `dns` module (the mainstream-client shape; inert in a flat config, ready the moment routing rules exist). Guarded by the new `PoisonGuardTests` (11 tests: the exact field-report verdict, SNI preservation, strict literal-IP parsing — `IPAddress.TryParse` alone accepts `188.114`! — and wire-format query/parse round-trips).
- **🕵️ Honest health probes — v0.4.28 hardens the v0.4.27 finding one layer deeper:** the probes were `http://` (port 80) while the real tunnel traffic runs **TLS on 443** — the audit's log showed the probe SUCCEEDING on 80 while the 443 handshake was being EOF'd, i.e. the app said «متصل» over a tunnel that carried nothing. All probe URLs (default **and** worker chain) are now **HTTPS**, so the health verdict exercises the same TLS layer as real traffic; the Degraded default absorbs the one extra TLS handshake (600 → **900 ms**; the worker plan's 2500 ms floor is untouched). `HealthProbePlanTests` now pins the scheme too.
- **⚙️ The audit's engine hardening set (Settings → Engines card):**
  - **TLS fragmentation (default ON, `net.fragment`)** — the Xray outbound gets `sockopt.fragment` (`tlshello`, 100–200 bytes, 10–20 ms) for TLS/REALITY dials over TCP transports: the ClientHello is split so DPI cannot fingerprint and RST it (the field logs were full of exactly those `wsarecv: connection forcibly closed` EOFs). Never applied to QUIC/mKCP (UDP has no ClientHello to split); a global switch, off-able when a server dislikes it.
  - **mux multiplexing (opt-in, `net.mux`)** — `mux.concurrency=8` on Xray for VMess/VLESS/Trojan/SS when the transport allows it; **never** with Vision flow, XHTTP or mKCP (where mux is invalid or harmful).
  - **TUN MTU (`tun.mtu`)** — the sing-box front-end's hardcoded 9000 is now a setting (9000/1500/1420/1380/1280), separate from the existing WireGuard MTU knob; the audit specifically called out that 9000 was untouchable.
- **📋 Engine trace:** Xray's own log level now follows the app (verbose setting → `debug`, otherwise `info`) instead of being pinned at `warning`, and connects log the effective verdict/fragment/mux decisions — the Logs page's engine filters now actually explain a failed dial.

## 0.4.21 — the Tunnels-page blank-screen hotfix (user: «بخش تونل کلا باز نمیشه») + the test that makes the crash class impossible to ship again
- **🩹 THE BUG — the Tunnels page opened to a completely blank screen.** Three hint labels in `ProfilesView.xaml` were written as `Style="StaticResource Subtle}"` — missing the opening `{`. The WPF markup compiler **accepts** such a string and defers it to load time, so the build stays green (0 errors) — but at runtime `InitializeComponent()` throws `XamlParseException` the moment the page loads, the global `DispatcherUnhandledException` handler swallows it (`Handled = true`), and you're left on a selected nav item with an empty gradient background. Exactly the reported symptom: everything else works, تونل‌ها never opens. The three lines are now `Style="{StaticResource Subtle}"` and the page loads.
- **🛡️ The class of bug can never ship again — `XamlIntegrityTests`.** The reason this slipped through: WPF XAML has a whole crash class that **compiles clean and only explodes at load time** — no C# error, no build error, no unit test touches it. The suite now statically re-validates every `.xaml` in the source tree on every test run:
  - a markup extension written without the opening `{` (`StaticResource`/`DynamicResource`/`Binding`/`x:Static`/…) → **test fails** (this exact incident),
  - a `{StaticResource Key}` that doesn't resolve in App/Controls/MainWindow/local keys, or that exists in only ONE theme dictionary (a blank page under the other theme) → **test fails**,
  - a `{l:T Key}` missing from `fa.json` or `en.json` → **test fails**,
  - malformed XML → **test fails**,
  - fa↔en key parity enforced (782/782).
  - On this incident's input the test fails with three precise messages naming the file, the attribute and the reason; on the fixed tree it's green.

## 0.4.17 — the OpenVPN flapping fix: it never actually started, and the recovery loop multiplied
- **🔁 THE bug (user report: «مینویسه که وصل میشه اوپن وی پی ان ولی بعدش شروع میکنه سریع قط و وصل شدن», field log `koalix-20261106_002.txt`).** Four root causes stacked on top of each other — all four fixed:
  - **openvpn.exe never survived a single start.** KOALIX passed `--management-client-bytecount 1` on the command line — but that is NOT a command-line option in OpenVPN 2.x; the client itself said so on every start: `Options error: Unrecognized option or missing or extra parameter(s) in [CMD-LINE]:1: management-client-bytecount (2.7.9)` → exit code 1, within ~250 ms. The option is gone; byte counters are now requested the documented way — over the management socket (`bytecount 1` → `>BYTECOUNT:` once per second), and real connection states too (`state on` → `>STATE: CONNECTED / RECONNECTING / EXITING / AUTH_FAILED…`), so the live speed cards work AND the log now shows OpenVPN's own progress instead of silence.
  - **"متصل" was a lie.** The health check for process-based engines fell back to a DIRECT internet probe — which answers from the UNTUNNELED network and succeeds on any online machine, even with the tunnel process already dead. KOALIX happily reported متصل, the 20-second monitor then found the corpse, restarted it, "connected" again, died again… the exact rapid قط‌ووصل the user saw. OpenVPN health is now STATE-BASED: the management `>STATE: CONNECTED` signal is the only truth — the UI cannot say متصل before the tunnel is genuinely up, a dead process fails instantly, and the monitor degrades/restores the UI from OpenVPN's own RECONNECTING/CONNECTED states instead of probing the internet beside the tunnel.
  - **The recovery loop multiplied exponentially.** Every (re)start of the OpenVPN engine added ANOTHER exit handler to the same process object, so after N restarts one exit raised N events — and since `TryTransition(Reconnecting)` succeeds as a no-op self-transition, every one of those events entered its OWN reconnect loop. The user's log: **5,518 «Reconnect attempt» lines**, hundreds of openvpn.exe starts, the same line logged dozens of times in the same millisecond, app effectively hung. Now: handlers are wired once (constructor, like every other engine), recovery is **single-flight** (one loop at a time — a second exit during a running recovery is ignored) and **generation-guarded** (a loop aborts the moment its connection is switched away or torn down — no more resurrecting engines the user already replaced).
  - **Deterministic crashes no longer get five blind retries.** An engine that dies within seconds of starting (bad options, missing binary, refused port) never heals by retrying — it now gets ONE calm retry instead of five, with a log line that says why («died right after start — bad config/binary?»), then an honest Error. Real mid-session drops keep the full 5-attempt exponential backoff.
- **🩹 Smaller OpenVPN repairs in the same pass:** the management reader used a 512-char buffer and split lines mid-read (counters silently dropped on long lines) — replaced with a real line reader; `AUTH_FAILED` now appears as a clear log line instead of a silent hang; temp `ovpn-run-*.ovpn` files from crashed runs are cleaned up on the next start; `--verb 3` is added when the .ovpn doesn't set its own log level, so field logs finally show OpenVPN's actual connection progress (the DEPRECATED/OPTIONS lines the user saw were the only output before).
- WireGuard/WireSock health semantics are untouched (the new interface members are default implementations — the WireSock process-alive model stays exactly as field-tested).

## 0.4.16 — the hang fix, the vanishing-servers fix, and a working OpenVPN
